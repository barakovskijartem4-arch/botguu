# CLAUDE.md

Правила работы в репозитории `botguu`.

## О проекте

Бот для студентов вуза:
- выдаёт расписание по группе (3 группы);
- показывает домашние задания с привязкой к расписанию и предмету;
- позволяет добавлять ДЗ.

Формат данных расписания и ДЗ и права на добавление ДЗ пока не утверждены. Ответы владельца на вопросы интервью фиксировать в разделе
«Принятые решения» ниже.

## Главное правило: сначала варианты, потом код

**Перед любой реализацией или правкой** (новая функция, изменение интерфейса бота,
структуры данных, архитектуры, рефакторинг) нужно показать владельцу **несколько
вариантов** (обычно 2–4) и **дождаться выбора**. Только после явного выбора
приступать к коду.

Как показывать варианты:

- **То, что напрямую увидит пользователь бота** (тексты сообщений, кнопки, меню,
  диалоги) — **картинками** (PNG): макеты чата бота. Под каждым вариантом 2–3 строки:
  чем хорош и чем плох. Отправлять через `SendUserFile`.
- **Всё техническое** (хостинг, деплой, база данных, архитектура, структура кода) —
  **только словами**, коротким списком вариантов с плюсами и минусами.
  Схемы и картинки для технических вещей **не рисовать**.

Не начинать писать код, не создавать файлы реализации и не менять существующие,
пока варианты не показаны и один из них не выбран. Если правка совсем мелкая
(опечатка, одна строка), всё равно коротко спросить разрешения.

Владелец может не знать технических деталей. Если его запрос технически требует
служебных действий (создать ветку, например `main`, добавить конфиг и т.п.),
их можно делать без отдельного согласования.

### Как делать картинки

- Сверстать макет чата бота в HTML и снять скриншот через Playwright
  (`require('playwright')`, `chromium.launch()`).
- Черновые файлы класть в scratchpad, а не в репозиторий.
- Подписывать варианты: «Вариант A», «Вариант B», …

## Общие правила

- Общение и тексты бота — на русском.
- Секреты (токен бота и т.п.) — только в `.env`, который в `.gitignore`.
  Никогда не коммитить токены.
- Данные (расписание, ДЗ) хранить отдельно от кода, в понятном для
  редактирования формате.
- Коммиты — с понятными сообщениями на русском или английском.
- Pull request не создавать без явной просьбы.

## Принятые решения

- Платформа: Telegram.
- Хостинг: Amvera (Railway отклонён). Бот работает через polling.
- База данных: SQLite в `/data/bot.db` (постоянное хранилище Amvera, не стирается
  при пересборке). PostgreSQL не нужен: данных мало. Файл базы не коммитится.
- Подключение к Telegram: необязательный прокси через переменную `TELEGRAM_PROXY`.
- Ответ на `/start`: вариант A3 «Коротко» — одно сообщение без кнопок:
  «Привет, {имя}! 👋 Я помощник твоей группы: скоро здесь будут расписание
  и домашка. Рад знакомству! ✨»
- Тексты бота не зависят от пола студента.

## Оформление репозитория

- README.md и другие .md-файлы оформлять красиво: заголовок по центру, бейджи
  (shields.io), эмодзи в заголовках разделов, таблицы, сворачиваемые блоки
  `<details>`, плашки GitHub (`> [!NOTE]`, `> [!TIP]`, `> [!WARNING]`).
- При добавлении функций обновлять таблицу «Возможности» и структуру проекта в README.
